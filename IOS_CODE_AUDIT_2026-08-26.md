# Grocery Benefits Tracker iOS — adversarial code audit

Date: 2026-08-26
Branch under review: `fix/ios-iap-ad-qa-hardening-20260826`

## Audit constraint

This review is advisory. It must not change the tracker’s business/backend logic or user interface. Release hardening may change native IAP/ad lifecycle, error handling, build configuration, tests, and release tooling only.

## Current findings

| Severity | Finding | Status | Recommendation |
| --- | --- | --- | --- |
| P1 | A banner load failure previously exhausted a short retry sequence and could stay absent for the rest of a supermarket session even after connectivity returned. | Fixed in release hardening | Keep capped long-lived retry (`2s → 5s → 15s → 30s → 60s → 2m → 5m`), reachability probing, captive-portal rejection, jitter, foreground recovery, and one-load-at-a-time locking. |
| P1 | If ATT/AdMob SDK startup fails while the app launches offline, the ad gate could become blocked before the banner retry subsystem exists. | Fixed in release assembly | Distinguish a transient SDK/network startup failure from a real privacy/ad-request block. Retry only the transient state; never retry a genuine privacy block as a network failure. |
| P1 | If StoreKit is unavailable at launch, entitlement can become `unknown`; ads correctly fail closed, but without recovery a free user could remain ad-free for the whole session and a paid user’s state would remain unresolved. | Fixed in release assembly | Keep entitlement `unknown` fail-closed and add capped foreground-only StoreKit recovery. Never infer `not-entitled` from a network failure. |
| P1 | Remove Ads pricing can drift in App Store Connect while StoreKit remains authoritative. | Fixed | Compare numeric StoreKit price only for USD storefronts against intended USD 9.99; warn without blocking purchase. Do not compare localized display strings across currencies. |
| P1 | The App Store download price and the Remove Ads IAP price can be confused because both appear in App Store Connect. The intended model is a free app plus a US$9.99 non-consumable. | Fixed in release gate | Require the U.S. app download to remain free and independently require `remove_ads_lifetime` to remain a US$9.99 non-consumable. Abort release on either drift. |
| P1 | A physical-iPhone QA path could lack explicit test-device configuration, while production must never inherit QA identifiers. | Fixed | Keep optional QA test-device IDs injected before Mobile Ads initialization and force an empty production list. Google’s official test banner remains the QA fallback. |
| P1 | Ads must disappear as soon as Remove Ads entitlement is verified. | Verified / hardened | Continue gating every banner mount/retry on exact `not-entitled` state; `checking`, `unknown`, and `entitled` must all suppress ads. |
| P1 | Line-total (`LINE_TOTAL`) items are handled correctly by `itemTotalCents()` during checkout, but report normalization and both history-correction paths determine “known price” using `unitPriceCents != null`. A valid line-total item can therefore become an “unknown-price” item in Reports after correction and can be excluded from corrected transaction `totalKnownCents`. | Open backend recommendation; not changed by auditor | Define one canonical `itemPriceIsKnown`/`itemTotalCents` invariant and use it in checkout, reports, history totals, correction totals, imports, and completeness calculations. Add regression tests for a line-total item whose `unitPriceCents` is null but `lineTotalCents` is valid. |
| P1 | Cash checkout validation can produce a plan with `cashDeltaCents > 0` while `cashPeriodForDate()` returns null. `applyCheckoutTransaction()` then silently skips the cash-budget update but still saves the transaction and cash allocation. A transaction date outside all stored budget periods can therefore understate cash spending. | Open backend recommendation; not changed by auditor | Make cash-period availability a checkout blocker whenever cash is allocated, or explicitly create/choose a deterministic cash period. `applyCheckoutTransaction()` should fail closed rather than silently skip a positive cash delta. |
| P2 | Historical cash correction is less fail-closed than SNAP/WIC correction. `reverseAllocations()` silently does nothing when the referenced historical cash period is missing, and `correctHistoryItemFunding()` likewise silently skips applying cash when the period cannot be found. | Open backend recommendation; not changed by auditor | Treat missing historical cash periods as a domain error/blocker, matching the existing SNAP/WIC missing-source behavior. Never save a correction whose cash reversal/application could not be posted. |
| P2 | Basket validation checks that each item has an ID but does not enforce ID uniqueness. `Object.fromEntries(plan.itemAllocations.map(...))` later keys allocations by item ID, so duplicate IDs can cause one item’s allocation array to overwrite another’s history allocation snapshot. | Open backend recommendation; not changed by auditor | Add a duplicate-item-ID blocker during basket normalization/checkout and validate imported/saved basket IDs before use. Keep generated IDs unique and fail closed on collisions. |
| P2 | Two rapid `complete-checkout` taps can enter `completeCheckout()` concurrently. Durable writes are serialized, but each queued candidate is calculated from the same stale pre-checkout state; the later candidate can replace the earlier transaction identity rather than deterministically rejecting the duplicate action. | Open backend recommendation; not changed by auditor | Add an in-flight checkout commit lock/idempotency token around validation → apply → durable commit. Revalidate the revision immediately before applying, and make repeated taps converge on the same transaction result. |
| P2 | Report reconciliation uses `new Date().toISOString().slice(0,10)` (UTC date) for “current”/expiry decisions while the tracker’s domain date helpers use local calendar dates. Around local midnight, recorded closing balances or WIC expiry state can be one day out of sync with the app. | Open backend recommendation; not changed by auditor | Use the same local-domain `isoDate()`/validated date-only helper everywhere a report compares against “today”; reserve UTC timestamps for recorded-at metadata only. Add near-midnight timezone tests. |
| P2 | `finishTransaction` failure can leave StoreKit transactions replaying on later launches. | Fixed | Keep three bounded exponential-backoff finish attempts after local entitlement is applied; if all fail, keep entitlement and let StoreKit replay rather than revoking the purchase. |
| P2 | Restore could previously reconcile immediately after `restorePurchases()` and briefly report `none` before a delayed restored transaction/current-entitlement update arrived. | Fixed | Keep the persistent StoreKit listener and the bounded post-restore entitlement settle window (`0ms`, `400ms`, `1200ms`, `2400ms`). A read failure reports restore failure; clean non-entitled reads may report none. Never grant entitlement speculatively. |
| P2 | Local notification reconciliation schedules desired reminders one by one and only removes stale reminders after scheduling. A mid-loop scheduling failure can leave a partial new schedule alongside the old schedule. | Open native recommendation | Make notification reconciliation transactional where practical: snapshot owned reminders, stage desired schedule, then reconcile/rollback on failure. Do not alter reminder semantics or UI. |
| P2 | Native + WebView “Clear All” is necessarily multi-store. A failure between native reminder/cache cleanup and web-store clearing can produce a partial clear unless the web layer retries/reconciles. | Open recommendation | Keep a durable request/acknowledgement protocol and make Clear All idempotent so repeating it always converges to an empty state. Audit the canonical web handler before changing anything. |
| P2 | Release assembly currently mutates `App.tsx`/test source during `embed-web-app.mjs` to layer outage hardening over a frozen source archive. This is deterministic but increases review drift risk. | Open release-engineering recommendation | After this release is proven on-device, fold the hardened native code and regression assertions directly into the canonical overlay/source archive, then retire the compatibility mutation and legacy two-retry verifier token. No UI/business-logic change is required. |
| P3 | Legacy-history migration can treat a zero-price known item as unknown (`price > 0`) and can multiply fractional legacy quantities directly by cents before later normalization. This is primarily a legacy-data edge case, not a current-entry path. | Open backend recommendation | Preserve an explicit `priceKnown` flag independently of whether the amount is zero, and route legacy totals through the same exact-cent total helper used by current entries. Add migration fixtures for $0 items and fractional quantities. |
| P3 | Several native paths intentionally swallow non-critical cleanup/share errors. Silent failures are safe for app continuity but can make field diagnosis difficult without analytics. | Open recommendation | Keep the app privacy-first; add only local/QA diagnostic counters and console diagnostics, never user identifiers or a new analytics backend. |

## Release invariants the auditor expects to remain true

1. Core grocery/SNAP/WIC tracking continues to work without a network connection.
2. Network, AdMob, ATT, App Store, or StoreKit failures must never block core tracker use.
3. `entitled`, `checking`, and `unknown` entitlement states never show ads.
4. Only a verified `not-entitled` state may enter the ad path.
5. Ads use non-personalized requests only.
6. No new UMP/GDPR flow is introduced by this hardening work.
7. Production contains no Google demo IDs as live production inventory and no QA test-device identifiers.
8. QA can use Google’s official test banner without a physical-device registration; optional test-device IDs remain QA-only.
9. StoreKit remains the customer-price authority; diagnostics never block a valid purchase because of a displayed-price comparison.
10. Commercial model remains: App Store download free; `remove_ads_lifetime` US$9.99 one-time; no subscription.
11. Audit recommendations do not alter the tracker’s domain/business logic or UI.

## Audit disposition

The release-specific ad/IAP hardening findings above are fixed or release-gated. The open backend/domain findings are pre-existing recommendations and were intentionally not changed by the audit track because this release is constrained not to alter the tracker’s business logic or UI. They should be handled in a separate logic-correction pass with dedicated regression tests before that code is changed.

The remaining blocker to a new TestFlight build is execution infrastructure: GitHub is currently rejecting both `macos-26` validation jobs before step 1, so there is no compiled result or runner log yet. Do not call the release green until a full test and production simulator validation has actually executed.
